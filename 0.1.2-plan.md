# 0.1.2-plan — Multiplayer: free lobby with painless registration (or no registration)

Planning-only artifact (no implementation yet). Subject: online multiplayer for
KeRot with a lobby that is free and easy to register — "without phone, google
account, etc" — or an alternative that needs no registration at all.

## 0. Requirements

- Free, or free at the scale of a hobby minigame (a few dozen concurrent players).
- Registration friction ≈ 0: email-only or GitHub OAuth at most (GitHub is already
  in use); **no phone verification, no Google-only signups, no credit card** — for
  the developer account. Players register **nothing**: they open a room code and play.
- Fits the existing runtime: classic scripts, zero deps in the game core, the sim
  is deterministic (`experiments/determinism.js`). Multiplayer may relax the
  `file://` rule for the *net layer only* (see §3).

## 1. Game structure: turn-based lockstep — the sim does the syncing

KeRot is almost uniquely easy to netcode: throws are discrete, the sim is
deterministic and frame-rate independent, and the world state is tiny.

- **Exchange only inputs**: each throw is `{seat, vx, vy}` (the stroke vector, which
  already has to be in `[vMin, vMax]`). Every client (and the relay, optionally)
  replays `stepWorld` identically. No state snapshots, no interpolation, no rollback.
- **Sequential turns** (curling-style alternation, e.g. seats alternate throws into
  the shared board; the round ends per the normal pool rules, score = ΣV per seat
  using puck ownership). Latency of hundreds of ms is invisible between throws.
- **Desync guard**: after every throw each client broadcasts a cheap state hash
  (e.g. FNV over `x, y, theta` at settle); on mismatch, resync from the host's
  compact state dump. Determinism means this should never fire.
- **Cheat surface**: none worth blocking in a casual game (a forged stroke is just
  a bad throw). If it ever matters: host-authoritative replay of the same inputs.

## 2. Transport interface (keep the game core untouched)

```
Net.open(roomCode, name)      Net.send(event)      Net.onEvent = fn
Net.close()                   Net.onPeers = fn
```

Two swappable backends behind the same tiny interface:

1. **WebSocket relay** — one room per connection group; the server relays JSON
   events and (optionally) validates turn order. Any §4 host can run it.
2. **P2P via Trystero** — WebRTC data channels with matchmaking piggybacked on
   public infrastructure (Nostr relays by default; MQTT/BitTorrent trackers as
   fallbacks). **No server of ours, no registration anywhere.** The host of the
   game is just another peer (acts as tie-breaker / state resync source).

## 3. Serving the client

- Single player stays `file://`-friendly as-is.
- Multiplayer needs a served page (ESM import of Trystero and/or `wss://`); ship it
  as the same static files on **GitHub Pages** (GitHub login already exists — zero
  new registration). Trystero is vendored as a local js file per repo policy
  (`vendor/trystero*.js`), never a CDN link.
- Rooms are joinable via URL: `index.html#room=ABCD` — open link, pick a nickname,
  play. No accounts, no email, nothing.

## 4. Hosting options for the relay (researched 2026-10)

| service | signup friction | free tier | WebSockets | verdict |
|---|---|---|---|---|
| **Cloudflare Workers + Durable Objects** | email only, no card | ~100k DO req/day, 13k GB-s/day, 5 GB SQLite | first-class (DO `acceptWebSocket`, hibernation = free idle lobbies) | **best hosted relay**: room code = DO id, stateful lobby rooms for $0; also free static hosting (Pages) |
| **Deno Deploy** | GitHub OAuth (no phone) | 1M req/mo, 15 CPU-h/mo (pauses if exhausted) | yes (`Deno.serve` upgrade) | **easiest to register** (GitHub only); fine for a small relay |
| **Render** free web service | email/GitHub, no card | 750 h/mo, 512 MB, sleeps after 15 min idle | supported, but free-tier long-lived sockets get flaky per reports | ok for dev/preview; cold starts ~1 min hurt a lobby |
| Northflank free sandbox | email | 2 always-on services | yes | decent; less proven |
| Railway / Fly.io / Koyeb | card or verification | credit-based | yes | **rejected**: card/phone friction |
| Glitch | — | — | — | **dead** (hosting shut down 2025-07) |

**Recommendation:** client on GitHub Pages (already-registered GitHub), relay on
Cloudflare Workers + Durable Objects (email-only signup, generous free WebSocket
rooms with hibernation) — or Deno Deploy if GitHub-only signup is the priority.
If even that is too much: **Trystero/Nostr path needs no hosting at all** (§2.2).

## 5. Protocol sketch (JSON over the Net interface)

```
c→*  {t:'hi', name}                 lobby: roster broadcasts
c→h  {t:'ready'}
h→*  {t:'start', cfg:{omega, muK, muS, recycleMode}, seed}   // identical worlds
c→*  {t:'throw', seat, vx, vy}      // applied between fixed steps, like today
c→*  {t:'hash', seat, hash}         // after each settle; mismatch → h sends {t:'sync', dump}
*→*  {t:'gg', scores}               // after final settle; per-seat ΣV breakdown
```

Implementation sketch (when executed): `js/net.js` (interface + protocol),
`js/net-ws.js` (relay client), `js/net-p2p.js` (vendored Trystero), `server/`
(~100-line Node relay: rooms, roster, turn order — also the Cloudflare DO class
variant), `js/game.js` gains a `seat` + remote-event path in `beforeSteps` only.
Lobby UI: room code box, nickname, ready button, roster list.

## 6. Open decisions (defaults chosen)

1. **Alternating-seat score** (each seat's own pucks, curling-ish) rather than
   co-op score or last-throw-wins — simplest meaningful competition on one board.
2. **2–8 players** — Trystero/WebRTC mesh and a small board both fall apart past 8.
3. Spectators = silent room members (cheap with a relay; free with P2P).
4. Rematch = new `start` event with a new seed; the lobby persists.
5. Reconnect: relay keeps the seat for 30 s and replays missed events from a ring
   buffer; P2P drops to "host re-sends state dump" (rooms are short).
6. Later, out of scope here: ELO/leaderboards (needs accounts — maybe a
   room-scoped results board reusing `experiments/results` ideas), simultaneous
   "speed rounds", server-side physics validation.
