# 0.7.5 worklog — Winner paint, the bot record, the shuffle, autoplay

Four requests, one task, no separate plan file: draw "amber" in its own colour on the
game-over card and add the player's/bot's type; keep each bot type's share of the whole
points in local storage as an EMA (`retriever: 0.6`); a special preset that draws random
game-related settings (and bots) while keeping the looks; and a button that autoplays
random all-bot games at max speed.

## 0. Review of 0.7.4 / 0.6.9

- 0.7.4 fitted the feed band `kv` around `autoOmega`'s 90 % hold rule. The shuffle draws
  μ and mass and re-solves ω through `autoOmega` (it never draws an ω of its own), so
  every shuffled board starts on the rule the band was fitted against — no refit, and
  the presets it mixes (`slick`, `grippy`, `stones`, `feathers`) are exactly the ones
  already measured.
- The one trap in this codebase was the result card's writer: `setText` writes
  `textContent`, and the headless smoke asserts on it (`resultWinner.textContent ===
  'draw'`, `'P4 '` in the score line). The painted line therefore writes the words as
  text first and the markup second — a browser keeps the paint, the smoke keeps the
  text, both read the same sentence.

## 1. Steps

1. **The card** (`js/ui.js`): `setWinner(plain, html)` puts `P2 amber wins (bot —
   balanced)` in as text and the same line painted — the name wrapped in its
   `seatColor`, the type dimmed in brackets — plus the same wording in the status line
   (`game over — P2 amber wins (bot — balanced) · double-click …`). A draw stays the
   bare `draw`.
2. **The record** (`js/record.js`, new): key `kerot.botShare`, `{"retriever": 0.6, …}`.
   A finished game's share for a type is the sum over that type's seats divided by the
   whole points of the table; one EMA step per game, `α = 0.25`, rounded to four
   decimals (two are shown). Storage is read/written through guards: without
   `localStorage` (a locked-down `file://`, node) nothing is stored and the line simply
   stays hidden — the game and the card are otherwise unaffected. `syncResult` gates it
   with `recorded` — one step per finished game, cleared when the state leaves
   `SCORED` — and adds `#resultEma`
   (`bot record · balanced 0.50 · blackhole 0.30 · retriever 0.15`, the types that just
   played, best first).
3. **The shuffle** (`js/presets.js`): `random: { label: 'random · shuffled game, bot
   table', random: true }` — a bundle that names no keys. `randomSetup()` draws them at
   apply time (once per applied game, never per frame): μk/μs (μs ≥ μk), mass
   (log-uniform, clamped), balls 1–4, disk schema (the score map is the rule), zone and
   hole shapes, return rule + swap, `scoreScale`, speed rule + vote mode, turn rule,
   bot speed, time-warp (p = 0.25, small tries), and a table of 2–4 distinct profiles
   from the eight bots, no human. The looks (theme, presentation, cards, decor,
   listener, volume) and the board geometry are not in the draw, so the shuffle keeps
   them by construction; `applySetup` expands it at the top with the draw *under* the
   setup's own keys, so `?preset=random&balls=7&seats=human,hunter` overrides the
   shuffle exactly like any other bundle, and the panel select and autoplay all draw
   the same way (the smoke pins `Math.random` to read the un-named drawn key back).
4. **Autoplay** (`js/auto.js`, new + `js/main.js`): the **Auto ▶** button in the
   transport bar arms it — `aria-pressed`, `■ Stop` while running, `.on` styling — and:
   applies the shuffle (an all-bot table), drops `CFG.botDelay` to 0 (the think delay
   is pure watching time; the search itself still runs at full strength, so the record
   stays comparable), and `Auto.frame(dt)` holds a finished board for 0.8 s — the result
   card and its record stay readable — then deals the next shuffle. Pause or the board
   editor freezes it (`Game.paused` covers both).
   Max speed lives in `main.js`: with `Auto.on` a frame runs up to **8 slices** of
   (tick + batch of ≤ **480** fixed steps) inside a **20 ms** wall budget instead of one
   tick + ≤ 96 steps, and stops at `scored`. Off, the loop is the shipped one, slice for
   slice.
5. **Surfaces**: `#resultEma` line and its CSS; the button; a help section ("the
   shuffle, autoplay and the bot record"); a README section; script order
   `record.js` before `ui.js`, `auto.js` before `main.js`.

## 2. Measurements

`node experiments/autoplay.js 6` (new — same table `keeper,hunter,balanced,retriever`,
classic board, same seeds, the frame loop of `main.js` in both settings; node is not
frame-paced, so "page s" is frames at 60 Hz, the pace the browser gives them):

| loop | frames/game | page s @60 Hz | cpu s/game | sim s/game |
| --- | --- | --- | --- | --- |
| shipped: 1 slice, ≤ 96 steps, think 0.7 s | 6939 | 115.6 | 10.7 | 115.6 |
| autoplay: 8 slices, ≤ 480 steps, 20 ms, no delay | 842 | 14.0 | 11.5 | 110.0 |

**8.2× the play speed at the same compute.** The shipped frames are mostly the bot
think delay — 0.7 s per throw, which autoplay drops — and the slice multiplies the rest;
the two runs play different trajectories (the delay also changes when the bot searches),
which is the ±6 % in cpu and sim. On the page the frames *are* the clock: a game falls
from ~2 minutes to ~14 s, and an autoplay frame stays inside its 20 ms budget on this
sandbox (typical frame ~10–15 ms, search frames the rare overrun).

## Next step

- The record is a per-type standing only. If autoplay ever shows a standings panel, add
  a game count per type (`retriever ×37`) so an early lucky game reads as what it is,
  or store the last result beside the EMA to draw a trend arrow.
- The 20 ms budget / 8 slices were fit on a 2-core sandbox with the bots' search as the
  rare overrun. On a phone the search costs more of the frame: measure
  `experiments/autoplay.js` there, and if frames overrun, cut the slice count first —
  the think delay removal is the free half of the speedup.
- `?preset=random` draws a fresh table every open. A `seed` key would make a shuffled
  game reproducible for a bug report (the game already runs on a seeded rng via
  `setRngState`); the URL could echo it.
- The hold (0.8 s) is a wall-clock constant: long enough to read the card on a desktop,
  tight on a phone. If it proves short, tie it to `prefers-reduced-motion` or make the
  card's tap deal the next game immediately (the double-click gesture already does this
  outside autoplay).
