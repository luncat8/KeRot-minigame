# 0.5 plan — speed play, and a bot that looks before it throws

Two bot settings, both off by default, both reachable from the panel, the URL and a
preset: how a seat votes the disk speed, and whether it plays its turn out in a copy of
the game before the real board commits to it.

## 1. Speed play — a strategy per seat, on top of its profile

A speed vote is priced once, in `speedWorth(cfg, om0, om, riders, throwW, omFrom)`: the
score the seat's own riders keep or lose at a candidate speed, the score the enemies' do,
and what the throw that follows has to park on. A strategy is a set of multipliers on
those terms — the arithmetic stays shared, so votes from two styles are still comparable.

```js
const SPEED_STRATS = {
	auto:   { label: 'read its own board', own: 1,   enemy: 1,   room: 1,   next: 0,   move: 1 },
	park:   { label: 'park — keep the disk slow', own: 1.7, enemy: 0.5, room: 1.5, next: 0.4, move: 1.2 },
	shake:  { label: 'shake — shed their riders', own: 0.8, enemy: 2,   room: 0.7, next: 0.8, move: 0.8 },
	tempo:  { label: 'tempo — swing with the order', own: 0.4, enemy: 0.4, room: 0.8, next: 1.8, move: 0.4 },
	still:  { label: 'never touch the speed', none: true },
};
```

- `speedStrat(cfg, name)` resolves a name (or `cfg.botSpeed`) to a row, falling back to
  `auto`; a row of `{ none: true }` makes `chooseVote` answer `VOTE_NONE` before it looks
  at the board, which is the whole of the `still` strategy and needs no other special case.
- `gatherRiders` weighs a rider by `own` or `enemy`; `throwWeight` multiplies its sum by
  `room` and adds `next · (opportunity + denial) / 2` signed by whether the seat throwing
  next is the voter. `chooseVote` subtracts `move · |Δω|` from the pick's value (never from
  the plateau, so a reluctance to move cannot invent a plateau).
- `chooseVote(profile, w, cfg, s, roster, next, rng, strat)` and `gatherRiders`/
  `throwWeight` take the strategy as an optional last argument, so a caller that wants a
  fixed strategy can pass one and the game just reads `cfg.botSpeed`.
- The consequence of `room` being signed is worth stating, because it reads backwards at
  first: with an *enemy* throwing next, a seat that weights room highly wants a *faster*
  disk — it is pricing the parking it takes away. `experiments/speed-vote.js` gates both
  directions (a round-rule board where parking wants slower, a turn-rule board where it
  wants faster).

## 2. Time-warp — the turn, played out in a copy

**The copy is a game.** `createGame(env)` takes `{ world, roster, cfg, sim }` and defaults
every field it is not given, so the page's `const Game = createGame({})` is unchanged and a
planner can pass a prebuilt world, roster and cfg. `sim` does three things: the seats are
aimed by `chooseStrokeQuick` instead of `chooseStroke`, no input or ghost is bound, and a
seat's turn is aimed and thrown in the same tick.

**What a snapshot has to hold.** The board (`cloneInto(saved, live.world)` — every typed
array plus the scalars, `cfg` excluded), and the flow around it: `state, turn, pending,
resolveT, voteT, botT, cfg.omega, omegaBase, rng.getState()`, plus each seat's `balls`,
`score` and `type`, and the game rng's state. `saveFlow(rec)` / `loadFlow(rec)` on the game
api are the only readers of those internals, which keeps `js/warp.js` from having to know
how a turn is sequenced. A copy runs on its *own* cfg object, because a closing vote writes
`cfg.omega` and two boards in one process would otherwise steer each other's disk.

**One candidate, then the next.** `begin(live, seat, rank)` snapshots and answers false when
there is nothing to compare (fewer than two lines) — then the caller throws the stroke its
own search picked and no frames are spent. Each try is `launch()`: reload the saved board
into the copy's world, restore the seats, `cfg.omega = flow.omega`, `loadFlow(flow)`, set
the aim, `commitThrow()`. The reload *is* the undo, so nothing in the live game has to be
reversible. Then frames of `8 × h` until the turn boundary, and `measure()` reads the result:

	value = (score[seat] + stableRate[seat] · future) − mean over the other seats
	        − the same expression on the snapshot, at the same `future`

`future = 2 + 0.9 · handoffT · (balls left at the snapshot)`, frozen at `begin`, is the
annuity ruler `chooseStroke` uses; the frozen copy of it is what makes the candidates'
numbers comparable. A line is taken as soon as `value ≥ warpGoal · ball`, where
`ball = π · puckR² · diskMeanRed · future`.

**Where the lines come from.** `chooseStroke(..., rank)` fills a per-group best table
(`makeStrokeRank`, `rankAdd`, `rankFinish`) as it searches, at no extra cost; the planner
takes those ranked lines in order — the greedy pick first, then each other group's best —
and once they run out, a fixed ladder of perturbations around the winner (`WARP_LADDER`:
±0.03 rad, then ±5 % of speed, then ±0.09 rad and the diagonals). The ladder is never
reached before the ranked lines are exhausted, so a short search is a coarse one rather
than a different one. `WARP_MAX_TRIES` (16) bounds the arrays; `warpTries` is clamped to it.

**The copy's other seats.** A rollout that searched would cost more than all its physics,
so `sim` seats aim with `chooseStrokeQuick(profile, w, cfg, i, rng, roster)`: the same
candidate groups, priced by the red of the spot each one lands on (`spotRate` through the
score's own quadrature, led by the throw's flight time) instead of a simulated flight. It
picks among the (radius, speed) pairs that are measured to lock from the launch lane at
every disk phase (`FEED_LOCK`), which is the rim capture, and it discounts a spot the disk
cannot hold a *stopped* puck on — friction has to drag the puck up to the surface speed
first, over a slide of `(ω d)² / 2 μk g`, which is the ~0.5 R capture limit.

**Frames, not one call.** `step(budgetMs)` works until the budget and returns "not yet";
`js/main.js` skips the frame's physics while `Game.planning` is true, so the board stands
still for the search and the stroke lands on the state it was computed against. A try is
read when its rollout ends, never when the budget expires, so where the frames are cut
cannot change the pick. The rollout has a fuse (`WARP_MAX_STEPS`) so no line can spin
forever, and a game that is over (`scored`, `settle`) ends every rollout at once.

**Cancel on any change.** Every entry point that can alter what the plan was computed
against (`setSeatTypes`, `setPuckMass`, `setDiskSchema`, `setVote`, `setSpeedRule`,
`giveBack`, `reset`, …) calls `cancelPlan()`, and `setWarp(false)` drops a running search
instead of honouring it. A cancelled plan restarts on the seat's next think, on the board
as it is then.

## 3. Settings

| key | default | meaning |
|---|---|---|
| `botSpeed` / `?botspeed=` | `auto` | how the seats vote the disk speed; `park`, `shake`, `tempo`, `still` |
| `warp` / `?warp=` | `false` | let a bot play its turn out before it throws it |
| `warpTries` / `?warptries=` | 6 | lines played out per turn, 1…16 |
| `warpTurns` / `?warpturns=` | 3 | turns a line plays out; 0 is to the end of the game |
| `warpGoal` / `?warpgoal=` | 0.5 | ball annuities of gain that end the search early; 0 takes the first line |
| `warpFrameMs` | 8 | work one frame spends on a search |

The panel groups them under *bot brain*, with the strategy select above the look-ahead and
its three sliders indented under a checkbox; the numbers the sliders hold are echoed in
their labels, and the search reports itself on the status line (`warpStatus`) rather than
in the canvas. Presets are made of the same keys, so `?preset=foresight` is a table built
to show the look-ahead and `?preset=speedplay` one built to show the strategies.

## 4. Files

- `js/vote.js` — `SPEED_STRATS`, `speedStrat`, the strategy arguments on `gatherRiders`,
  `throwWeight`, `chooseVote`.
- `js/bots.js` — `makeStrokeRank` / `rankAdd` / `rankFinish` (the shortlist a search leaves
  behind), `chooseStrokeQuick` and `spotRate` (a policy that prices a spot, not a flight),
  `FEED_LOCK`.
- `js/game.js` — `createGame(env)` and its `sim` mode, `saveFlow` / `loadFlow`,
  `rngState` / `setRngState`, `startPlan` / `stepPlan` / `cancelPlan`, `setWarp`, `planning`,
  `warpStatus`.
- `js/warp.js` — the planner: snapshot, candidate ladder, rollout, accept rule, frame
  budget, the status sentence. Owns its copy's world, roster and cfg, allocated once.
- `js/cfg.js`, `js/presets.js`, `js/ui.js`, `index.html` — the settings and the panel.
- `experiments/time-warp.js` — the gates below; `experiments/vote-rules.js` — the same
  table of games per strategy; `experiments/speed-vote.js` — the strategy directions.

## 5. Properties the implementation has to have

1. With `warp: false` and `botSpeed: 'auto'`, nothing changes: the same strokes, the same
   votes, the same frames — `chooseStroke`/`chooseVote` answers are byte-identical to the
   previous release, which is measurable by diffing the picks on fixed boards.
2. A copy plays a turn exactly as the game does: same strokes in, same positions, pucks,
   scores, disk phase and clock out, bit for bit, at the turn boundary.
3. Every candidate starts from the same slate — a rollout must leave nothing for the next
   one, including the seats' votes — so the value of a line measured on its own equals the
   value the search gives that line.
4. The search's line is never worth less than the greedy line on its own measure, and
   `warpTries: 1` is provably the same game as no look-ahead.
5. Planning does not touch the live board: while a search runs, its world is byte-identical
   frame to frame, and the frames it spends do not advance the game's clock.
6. Cutting the search over frames does not change what it picks, and one frame's work stays
   near `warpFrameMs`.
7. A game with the look-ahead on still reaches `scored` within its throw cap, and a
   strategy named `still` never moves the disk.
