# 0.5 draft — speed play, and a bot that looks before it throws

User prompts for this round:

```
read archive/0.1.8-worklog.md and react to what is written there.
idea: varying the voted speed is itself a tactic:
down-down-push (a pluck is in a risk position) - keep-keep - (another player pushes his
pluck out of score zone) - up-up-down-down-push-...
So it can be interesting to have some different speed strategies to pick.

Next implement new bot settings: time-warp calculation. if enabled the bot can undo turn
if result is not good and try until desired goal achieved. (headless calculation, then
apply to real game). limit num of try
```

## Reading of the prompts

- **0.1.8's conclusion is the starting point.** That plan decided that a speed-up is a
  trade and not a good move: the same ramp that sheds an enemy rider sheds your own, and
  the disk's value is priced per seat from what each of them has riding. The idea in the
  first prompt is the next step of the same thought — if the price is a trade, then *how*
  a seat weighs it is a style of play, and different weights should be worth picking
  between. So this is not a new evaluation to invent: it is the existing one with its
  terms exposed as a choice.
- **A strategy is a set of weights on the terms the vote already prices**, not a separate
  policy engine: what my own riders are worth (`own`), what the enemies' are worth
  (`enemy` — negative for a seat that likes shedding them), what the next throw has to
  park on (`room`), whose throw comes next (`next`), and how much a moving disk costs
  (`move`). Five numbers per profile, read from one table, is enough to make seats that
  behave visibly differently, and it keeps the votes comparable between styles because
  they all come out of the same `speedWorth`.
- **The examples in the prompt are sequences, and sequences are a schedule.** "down-down-
  push, then keep-keep, then up-up-down-down-push" is a seat doing something *because of
  what it did last turn* — the piece that four weights cannot express. The one schedule
  term kept is `next`: a seat that plays the throw coming after its own (a push is worth
  more when the disk speed you voted for is the speed *you* will throw under). A memory
  of the last votes was left out deliberately; it would be a state to reset and a thing
  for a bot to be punished for.
- **"Undo the turn if the result is not good" is a search over a saved state, not a
  rewind of the live one.** The bot takes its turn in a *copy* of the game, reads what
  happened, and either keeps or throws away the copy; the real board is handed only the
  stroke that won. "Undo" is then free — the next candidate starts from the same saved
  state — and the live game never has to be repairable, which is the part that could not
  be made safe.
- **"Headless calculation, then apply to the real game" means the copy is the game.** The
  thing being simulated has to be `js/game.js` and not a model of it, or the look-ahead
  drifts from the rules on the first change to either. So `createGame` gains an
  environment argument (world, roster, cfg, and a `sim` flag), and a planner builds its
  copy through the same factory the page uses. The page holds the real board still while
  the copy works, so the stroke lands on exactly the state it was planned against.
- **"Until desired goal achieved. limit num of try" are two limits, and they are settings.**
  A line is good enough when it is worth `warpGoal` more than the position the search
  started from, measured in ball annuities (the same ruler `js/bots.js` prices a throw
  on), and the search stops after `warpTries` lines however good they are. Both belong to
  the bot, not to the difficulty, and neither is on by default.

## Decisions

- **Goal against the position, not against the lead.** An aspiration bar over the greedy
  line's value is satisfied by definition (the greedy line *is* the best one-ply line),
  and a bar on the absolute lead means a bot that is winning 200–0 stops searching forever
  and one that is losing searches forever. The number that means "this turn was worth
  playing" is what the rollout gained over the snapshot, so that is what `warpGoal` is
  compared to, with the *same* `future` horizon for every candidate — otherwise a line
  whose rollout happened to end with more balls left on the board is priced on a longer
  ruler than its neighbour.
- **What is searched is the bot's own shortlist.** `chooseStroke` already keeps the best
  stroke of each of its groups; the planner plays those out, best first, then a ladder of
  perturbations around the winner (half a degree of aim, 5 % of speed, then wider). The
  first candidate is the greedy line, so `warpTries: 1` is the same game as no look-ahead,
  and that is a gate rather than a hope. A search that only replaced the pick would throw
  away the fine tuning; one that only refined it would agree with the one-ply pick too
  often.
- **The copy's other seats play a policy, not a search.** A rollout is worth about 0.5 ms
  of physics for 4 s of a sparse board, and one `chooseStroke` is ~190 ms — if the seats
  answering in a rollout searched, a look-ahead would cost more than the game it is
  planning. So a copy runs `chooseStrokeQuick`: the same candidate groups, priced by the
  red of the spot they land on instead of a simulated flight. The consequence is written
  into `js/warp.js`: the look-ahead is optimistic about the reply it gets, and it is
  allowed to be, because it is comparing its own lines against each other.
- **The frames the search runs in are the page's frames.** One frame does `warpFrameMs` of
  work and returns; where the cut falls cannot change the outcome, because a line is read
  when its rollout ends and never when the budget expires. `warpTries: 6` at three turns
  is ~90 ms of held board, which is 11 frames at 8 ms — visible as a think, not as a
  stutter.
- **The look-ahead is off by default and its settings are keys.** `botSpeed` (a strategy
  name, `auto` default), `warp` (0/1), `warpTries`, `warpTurns` (0 = play the copy out to
  the end of the game), `warpGoal` — all of them in the panel, in the URL, and in presets,
  so a table can be shared with the brain switched on.

## Not in this round

- The planner does not plan its *own* later throws: a rollout answers the seat's stroke and
  then plays the rest of the horizon with policies, so a line that is good because the bot
  will follow it up next turn is not credited. That is the same one-turn horizon
  `chooseStroke` already prices on, extended to the replies.
- Votes the human has not cast yet cannot be known, so a copy lets the seats that would be
  human abstain. A bot planning against a human who is about to double the disk speed is
  planning against nothing.
- One strategy per table, not per seat: `botSpeed` is a rule the seats share, so a table is
  a style of play rather than a roster of five different ones.
