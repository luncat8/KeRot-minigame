# 0.8-multiplayer-plan — Multiplayer: free lobby with painless registration (or no registration)

Planning-only artifact (no implementation yet). Subject: online multiplayer for
KeRot with a lobby that is free and easy to register — "without phone, google
account, etc" — or an alternative that needs no registration at all.

## 0. Requirements

- Free, or free at the scale of a hobby minigame (a few dozen concurrent players).
- Registration friction ≈ 0: email-only or GitHub OAuth at most (GitHub is already
  in use); **no phone verification, no Google-only signups, no credit card** — for
  the developer account. Players register **nothing**: they open a room code and play.
- Fits the existing runtime: classic scripts, zero deps in the game core, the sim
  is deterministic (`experiments/determinism.js`). Multiplayer may relax the
  `file://` rule for the *net layer only* (see §3).

## 1. Game structure: turn-based lockstep — the sim does the syncing

KeRot is almost uniquely easy to netcode: throws are discrete, the sim is
deterministic and frame-rate independent, and the world state is tiny.

- **Exchange only inputs**: each throw is `{seat, vx, vy}` (the stroke vector, which
  already has to be in `[vMin, vMax]`). Every client (and the relay, optionally)
  replays `stepWorld` identically. No state snapshots, no interpolation, no rollback.
  Human speed votes are inputs too (§5): `{seat, kind, value}`, broadcast like a
  throw and tallied identically on every client.
- **Sequential turns** (curling-style alternation, e.g. seats alternate throws into
  the shared board; the round ends per the normal pool rules, score = ΣV per seat
  using puck ownership). Latency of hundreds of ms is invisible between throws.
- **Host-serialized turns (default)**: clients send their throw **to the host only**.
  The host validates turn order and broadcasts `{t:'throw', seq, seat, vx, vy}` in
  order. A turn does not advance until the host has broadcast the previous throw, so
  every client applies throws in the same order without any peer-to-peer ordering
  machinery. The relay path gets in-order delivery per room for free; the P2P mesh
  still needs `seq` numbers, a small reorder buffer and retransmission of missing
  events, but never has to decide turn order itself.
- **Desync guard**: after every throw each client broadcasts a cheap state hash
  (e.g. FNV over `x, y, theta` at settle). On mismatch, the client asks the resync
  source for a state dump **tagged with the throw sequence number** it is missing
  (`{t:'sync', seq, dump}` — the dump is the state after throw `seq`); a dump for a
  later `seq` is refused, so a lagging client cannot pull the host past the point it
  is trying to rejoin at. Determinism means this should never fire.
- **Resync source**: the host is the resync source while it is in the room. If the
  host leaves, the peer with the lowest seat index among those that have applied the
  most throws becomes the source (elected deterministically from the roster and the
  `seq` each peer has acknowledged — no voting round needed). P2P rooms are short,
  so a dump is always cheap.
- **Stall protection**: a turn with no throw is not allowed to freeze the room. The
  host runs a per-turn timer (a few seconds past the normal handoff); when it fires
  the seat's turn is forfeited (skipped, ball returned) and the turn moves on. A
  peer that disconnects mid-turn is treated the same way after its seat's retention
  window expires (§6.5). This is the only anti-grief rule needed: a forged stroke is
  just a bad throw, and the state is public to every client anyway.
- **Cheat surface**: none worth blocking in a casual game. If it ever matters: the
  host-authoritative ordering above already makes the host the single point that
  decides what is applied; server-side physics validation would be a later layer.

## 2. Transport interface (keep the game core untouched)

```
Net.open(roomCode, name)      Net.send(event)      Net.onEvent = fn
Net.close()                   Net.onPeers = fn
```

Two swappable backends behind the same tiny interface:

1. **WebSocket relay** — one room per connection group; the server relays JSON
   events, serializes turns and validates turn order. Any §4 host can run it.
2. **P2P via Trystero** — WebRTC data channels with matchmaking piggybacked on
   public infrastructure (Nostr relays by default; MQTT/BitTorrent trackers as
   fallbacks). **No server of ours to register on, no player registration
   anywhere** — but this is not "no infrastructure": matchmaking rides third-party
   Nostr relays, connectivity needs public STUN and can fail behind strict NAT
   without a TURN server, and those relays are subject to their own rate limits and
   policies. The host of the game is just another peer (acts as turn serializer /
   state resync source, with the §1 election as fallback). A P2P room that cannot
   establish enough channels falls back to telling the player to use the relay path.

## 3. Serving the client

- Single player stays `file://`-friendly as-is.
- Multiplayer needs a served page (ESM import of Trystero and/or `wss://`); ship it
  as the same static files on **GitHub Pages** (GitHub login already exists — zero
  new registration). Check the repo's Pages setup before relying on it: Pages
  hosting of a private repository is restricted, and the site must be reachable
  publicly for room links to work. Serving over HTTPS is required for `wss://` and
  WebRTC and is what Pages gives. Trystero is vendored as a local js file per repo
  policy (`vendor/trystero*.js`), never a CDN link.
- Rooms are joinable via URL: `index.html#room=ABCDEFGH` — open link, pick a
  nickname, play. No accounts, no email, nothing. Codes are **8+ characters**
  (base32): the relay can check a code against its own room table, but P2P
  matchmaking on a public relay cannot, and a 4-character code collides within a
  few rooms.

## 4. Hosting options for the relay (researched 2026-10 — re-verify the limits at implementation time)

| service | signup friction | free tier | WebSockets | verdict |
|---|---|---|---|---|
| **Cloudflare Workers + Durable Objects** | email only, no card | ~100k DO req/day, 13k GB-s/day, 5 GB SQLite | first-class (DO `acceptWebSocket`, hibernation = free idle lobbies) | **best hosted relay**: room code = DO id, stateful lobby rooms for $0; also free static hosting (Pages) |
| **Deno Deploy** | GitHub OAuth (no phone) | 1M req/mo, 15 CPU-h/mo (pauses if exhausted) | yes (`Deno.serve` upgrade) | **easiest to register** (GitHub only); fine for a small relay |
| **Render** free web service | email/GitHub, no card | 750 h/mo, 512 MB, sleeps after 15 min idle | supported, but free-tier long-lived sockets get flaky per reports | ok for dev/preview; cold starts ~1 min hurt a lobby |
| Northflank free sandbox | email | 2 always-on services | yes | decent; less proven |
| Railway / Fly.io / Koyeb | card or verification | credit-based | yes | **rejected**: card/phone friction |
| Glitch | — | — | — | **dead** (hosting shut down 2025-07) |

**Recommendation:** client on GitHub Pages (already-registered GitHub), relay on
Cloudflare Workers + Durable Objects (email-only signup, generous free WebSocket
rooms with hibernation) — or Deno Deploy if GitHub-only signup is the priority.
If even that is too much: **Trystero/Nostr path needs no hosting of ours at all**
(§2.2), with the relay as the fallback when P2P connectivity fails.

## 5. Protocol sketch (JSON over the Net interface)

```
c→h  {t:'hi', name}                 lobby: join request, roster broadcast
c→h  {t:'ready'}                    lobby: seat is ready
h→*  {t:'start', seq:0, cfg, seed}  // cfg = the FULL canonical setup (geometry,
                                     // omega, μ, mass, schema, recycle, zones, holes,
                                     // diskScale, balls, maxThrows, vote rule/mode,
                                     // botspeed, warp + its numbers, seats); every
                                     // client hashes it and aborts the match on mismatch
c→h  {t:'throw', seat, vx, vy}     // to the host only; never broadcast directly
h→*  {t:'throw', seq, seat, vx, vy} // host-serialized, in order; clients apply by seq
c→*  {t:'vote', seat, kind, value}  // a human's speed vote, an input like a throw
c→*  {t:'hash', seat, seq, hash}    // after each settle; mismatch → request {t:'sync', seq}
c→h  {t:'sync', seq}                // ask the resync source for the dump of throw seq
h→*  {t:'sync', seq, dump}          // compact world state after throw seq (never newer)
h→*  {t:'turn', seat}               // the host opens the next turn (after throw seq N)
*→*  {t:'gg', scores}               // after final settle; per-seat ΣV breakdown
```

Implementation sketch (when executed): `js/net.js` (interface + protocol),
`js/net-ws.js` (relay client), `js/net-p2p.js` (vendored Trystero), `server/`
(~100-line Node relay: rooms, roster, turn serialization, ring buffer — also the
Cloudflare DO class variant), `js/game.js` gains a `seat` + remote-event path in
`beforeSteps` only. Lobby UI: room code box, nickname, ready button, roster list.
Remote seats: each client renders only its own aim; a remote human seat shows a
"waiting for Pn" state with the think timer, so a slow opponent is visible, not a
frozen board.

## 6. Open decisions (defaults chosen)

1. **Alternating-seat score** (each seat's own pucks, curling-ish) rather than
   co-op score or last-throw-wins — simplest meaningful competition on one board.
2. **2–8 players** — Trystero/WebRTC mesh and a small board both fall apart past 8.
3. Spectators = silent room members (cheap with a relay; free with P2P).
4. Rematch = new `start` event with a new seed; the lobby persists.
5. Reconnect: the relay keeps the seat for 30 s and replays missed events from a
   ring buffer (the `seq` numbers make the replay exact); after the window the seat
   is forfeited and the turn timer (§1) moves the room on. P2P drops to "resync
   source re-sends the state dump" (rooms are short; the §1 election covers a
   departed host).
6. Later, out of scope here: ELO/leaderboards (needs accounts — maybe a
   room-scoped results board reusing `experiments/results` ideas), simultaneous
   "speed rounds", server-side physics validation.
